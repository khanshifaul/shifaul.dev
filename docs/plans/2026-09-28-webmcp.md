# Plan: WebMCP for shifaul.dev

**Date:** 2026-09-28
**Target:** `frontend.shifaul.dev` (Next.js 16.2.6, React 19.2.4, Vercel) + optional backend phase
**Status:** approved for implementation

## What WebMCP is (research summary)

WebMCP is a proposed Chromium API that lets a page register structured "tools"
(name + description + JSON Schema + `execute` callback) that browser AI agents
can discover and call — an in-page, tab-bound MCP server.

- Spec: <https://webmachinelearning.github.io/webmcp> · Chrome docs: <https://developer.chrome.com/docs/ai/webmcp>
- Current surface: **`document.modelContext.registerTool()`** (imperative) and
  HTML form annotations (`toolname`, `tooldescription`, `toolparamdescription`,
  `toolautosubmit`) (declarative).
  ⚠️ `navigator.modelContext` was **removed in Chromium 150** — never use it.
- Availability: Chrome 149+ origin trial / `chrome://flags/#enable-webmcp-testing`
  in earlier previews. No other browser ships it yet → **all usage must be
  feature-detected and fail silently.**
- Hard requirements: HTTPS (✅ Vercel), **origin isolation**
  (`Origin-Agent-Cluster: ?1`, no `document.domain`), Permissions-Policy
  `tools` (defaults to `self` = top-level + same-origin only, which is what we want).
- Tools are **ephemeral**: they exist only while a tab is open. For headless /
  always-on agents we need a server-side MCP (Phase 4 below) — WebMCP does not
  replace it.

## Goal

When a visitor opens shifaul.dev with an agent-enabled browser, the agent can
answer "what has he built?", "is he available?", "show his Rust work" and
perform "contact him" **by calling typed tools** instead of scraping the DOM.

## Tool catalog (v1)

Read-only (safe, `annotations.readOnlyHint: true`):

| Tool | Input | Backed by |
|---|---|---|
| `search_projects` | `{query?, tags?, limit?}` | `projectsAPI.getPublicProjects` |
| `get_project` | `{slug}` | `projectsAPI.getPublicProjectBySlug` |
| `search_posts` | `{query?, tag?, limit?}` | `blogAPI.getPublicBlogPosts` |
| `get_post` | `{slug}` | `blogAPI.getPublicBlogPostBySlug` |
| `get_profile` | `{}` | site config + about/resume copy (static) |
| `navigate` | `{path}` (enum of public routes) | `router.push` |

Write tools (human-in-the-loop, `readOnlyHint: false`):

| Tool | Behavior |
|---|---|
| `submit_contact` | Validates with zod → **prefills `/contact` and returns `status: "awaiting_user_confirmation"`**; never silently submits. Confirmation happens in the visible UI. |
| `subscribe_newsletter` | Same pattern: prefills the newsletter field, user clicks confirm. |

Design rule: **tools may stage actions, only the human commits them.** This
matches Chrome's guidance (user stays in the loop) and removes the
abuse surface (no unauthenticated POSTs triggered by an agent).

## Architecture

```
frontend.shifaul.dev/
├── lib/webmcp/
│   ├── types.ts            # ToolDefinition mirroring MCP Tool shape
│   ├── registry.ts         # feature-detect + register/unregister + zod validation
│   ├── schemas.ts          # zod schemas, single source of truth → JSON Schema
│   └── tools/
│       ├── portfolio.ts    # search_projects, get_project
│       ├── blog.ts         # search_posts, get_post
│       ├── profile.ts      # get_profile, navigate
│       └── actions.ts      # submit_contact, subscribe_newsletter
├── components/providers/webmcp-provider.tsx   # client component, mounts registry
├── app/layout.tsx          # add <WebMCPProvider /> (inside StoreProvider)
├── next.config.ts          # headers(): Origin-Agent-Cluster, Permissions-Policy
├── public/llms.txt         # static agent-facing site description
└── docs/plans/2026-09-28-webmcp.md
```

`WebMCPProvider` is a client component that:

1. Feature-detects `document.modelContext?.registerTool` → no-op if absent.
2. Registers tools once on mount.
3. Re-registers on route change (`usePathname`) so `navigate` and page-scoped
   tools always reflect the current view (the API requires re-registering the
   full set; registration rejects duplicate names).
4. Unregisters on unmount (SPA navigation must not leak stale tools).

JSON Schema is derived from zod via a tiny hand-rolled converter in
`schemas.ts` (zod v4 ships `z.toJSONSchema()` natively — use that, no new dep).

## Steps

1. **Headers** — `next.config.ts` → `async headers()`:
   - `Origin-Agent-Cluster: ?1` on all HTML routes (WebMCP is disabled without origin isolation).
   - `Permissions-Policy: tools=(self)` (explicit; default already self).
   - Verify in DevTools → Application → Frames after deploy.
2. **Core module** — `lib/webmcp/types.ts`, `schemas.ts`, `registry.ts`
   (feature detection, zod-validated `execute`, error → structured `{error}` result, no throws across the boundary).
3. **Read-only tools** — `tools/portfolio.ts`, `tools/blog.ts`, `tools/profile.ts`
   reusing existing `lib/actions/*Api.ts` fetchers (they already handle the
   `blogposts.json` fallback).
4. **Provider + wiring** — `components/providers/webmcp-provider.tsx`, mount in `app/layout.tsx`.
5. **Declarative API** — annotate `components/contact/_components/ContactForm.tsx`
   and the newsletter form with `toolname`/`tooldescription`/`toolparamdescription`
   so agents get the form path even before JS registers anything. (Confirm exact
   attribute spelling against `node_modules/next/dist/docs` + Chrome docs at build time — the declarative surface is still moving.)
6. **Write tools with confirmation** — `tools/actions.ts` (stage + confirm pattern above).
7. **Discovery assets** — `public/llms.txt` (+ reference in `robots.txt`) describing
   the site, main routes, and that WebMCP tools exist. Cheap, spec-independent.
8. **Verification** (see below).

## Constraints & risks

- **AGENTS.md rule applies:** Next.js 16 has breaking changes — read
  `node_modules/next/dist/docs/` before touching routing/layout code
  (`proxy.ts` already replaces `middleware.ts`; `headers()` behavior must be
  checked against these docs).
- **API churn:** spec is CG draft; `document.modelContext` vs future surface may
  change. Mitigation: all platform contact isolated in `registry.ts` — one file
  to update.
- **No new runtime deps for v1.** Polyfill (`@mcp-b/webmcp-polyfill`) only as
  Phase 3, behind `NEXT_PUBLIC_WEBMCP_POLYFILL=1`, because it registers tools in
  browsers that can't act on them.
- **Security:** never expose admin/protected APIs as tools; never return auth
  tokens; cap tool output size; treat all returned post content as untrusted
  text (indirect prompt-injection guidance: <https://developer.chrome.com/docs/ai/webmcp/secure-tools>).
- **Vercel:** confirm custom headers pass through `next.config.ts` (they do) and
  are not overwritten by edge config.

## Verification

1. `bun run lint` and `bunx tsc --noEmit`.
2. Feature-detection unit test: registry no-ops when `document.modelContext` is undefined (jsdom default).
3. Per-tool test: zod schema rejects bad input; `execute` with mocked fetch returns capped JSON.
4. Manual, Chrome 149+: enable flag/origin trial → install **Model Context Tool
   Inspector** extension → open `www.shifaul.dev` → confirm all 8 tools listed →
   run `document.modelContext.getTools()` in console → call
   `executeTool('search_projects', '{"query":"rust"}')`.
5. Evals (per Chrome's WebMCP evals doc): prompt an agent with 3 user intents
   ("find his AI projects", "read his latest post", "draft a contact message")
   and confirm it picks the right tool + valid args.
6. Regression: site must behave identically with WebMCP absent (all consumers feature-detected).

## Phases

- **P1 (this plan):** headers, read-only tools, provider, declarative forms, llms.txt.
- **P2:** write tools with stage/confirm.
- **P3:** optional MCP-B polyfill flag for non-Chromium testing.
- **P4 (separate plan):** server-side MCP (`POST /api/mcp`, Streamable HTTP) in
  the backend or as a Next route handler so headless agents (Claude, Cursor) can
  query portfolio/blog without a browser tab. WebMCP and MCP complement each
  other — same tool schemas can be reused.
